# 03 — Daily Run

*The **execution shape** of the pipeline. The run is agent-driven end to end:
`/atd-daily` (canonical `agents/orchestrator.md`) sequences it, and the Trader
subagent — `agents/trader.md` — executes the call. This file is what that recipe
binds to: input order, output spec, header-block contract.*

**Scope: one sleeve per run.** If you run more than one account, give each its own copy
of this file and its own scheduled task. Do not evaluate another sleeve's tickers or
write to its files.

**Output file:** `output/evaluation_<date>.md` (e.g. `output/evaluation_2026-08-15.md`)
— dated, accumulates across runs.

---

## Invocation — the whole run is one instruction

**`/atd-daily`.** It executes this file's execution shape end to end — Phase A
(`tools/run_daily.py`), Analyst, Trader, the mechanical review
(`tools/eval_reviewer.py`), the Reviewer, up to three defect rounds, then the
ledger *draft*. It halts rather than routing around a failure, and it never
commits to the ledger.

The wrappers live alongside this repo:

| Platform | `/atd-daily` command | Trader subagent |
|---|---|---|
| Claude Code / Cowork | `.claude/commands/atd-daily.md` | `.claude/agents/trader.md` |
| opencode | `.opencode/command/atd-daily.md` | `.opencode/agent/trader.md` |

All four are generated by `python3 tools/sync_agents.py` from the canonicals
`agents/orchestrator.md` (the run sequence) and `agents/trader.md` (the call).
The canonical is the **single source of truth**; edit it and re-run the sync to
ship to both platforms. Drift is caught with
`python3 tools/sync_agents.py --check`.

> **There is one execution mode, and it is the agent.** The file-driven
> narration this document used to carry as *Appendix A* — "Steps 0–10", read by
> a scheduler or an LLM as prose instructions — was retired on 2026-08-23. Every
> rule it held lives in a canonical that is read fresh on each run: the call in
> `agents/trader.md`, the gates in `rules/02_SLEEVE_RULES.md`, the source
> contract in `docs/DATA_SOURCES.md`, the sequence in `agents/orchestrator.md`.
> Two documents of the same recipe is one document that silently goes stale, and
> the step numbers outlived the steps.

> **Which file owns what.** The *sequence and its gates* live in
> `agents/orchestrator.md`. The *execution shape and output contract* live here.
> The *method* lives in `rules/01_METHOD.md` and `rules/02_SLEEVE_RULES.md`. An
> orchestrator that starts encoding gate mechanics is drift — push it down into
> the rulebooks, where the Trader reads it fresh every run.

## Roles — three-subagent pipeline

Each run is owned by **three subagents**. Each has a different context. The output
of one is the input to the next. None self-assesses.

- **Analyst** *(subagent — `agents/analyst.md`)* owns **data ingestion**: source
  config, running facts/fundamentals/xray scripts, FAIL/PARTIAL/NONE row
  resolution against `docs/DATA_SOURCES.md`, theme news, and the dated handoff
  `output/data/analyst_<date>.md`. Has no opinion on any investment call. Never
  applies gate cards.
- **Trader** *(subagent — `agents/trader.md`)* owns **the call**: reads the
  Analyst handoff, the rotation read, the rulebooks (fresh every run), applies
  the gate cards, writes `output/evaluation_<date>.md` with one explicit
  signal per roster name and written levels on every actionable line.
- **Reviewer** *(subagent — `agents/manager.md`)* owns **the pre-save
  check**: verifies the Trader's draft against roster, facts sheet, sector x-ray,
  format and structural rules. Returns numbered defects. Never edits.

> The Analyst and Reviewer are subagents because each has a context **different
> from the Trader's** — that independence is the product. The Trader is a
> subagent because its judgement is one continuous read-the-roster-and-write-
> calls flow, and running it as an agent buys loop recovery on partial failure,
> in-place access to the previous run's state, and rulebook-drift observability.

## Rulebooks — read fresh every run

The Trader's contract is the union of:

1. The rulebooks the Trader reads fresh every run: `rules/01_METHOD.md`, `rules/02_SLEEVE_RULES.md`.
2. The data-source contract the Analyst reads fresh every run: `docs/DATA_SOURCES.md`.
3. The Trader's own canonical: `agents/trader.md`.
4. The output contract — the "Output spec" section below.
5. The report template the Trader follows exactly: `templates/evaluation.template.md`.

When the rulebooks change, **the change ships when the next Trader reads them**.
You do not need to update the Trader canonical for rule changes — that's the
whole reason rules are file-resident. Update the rulebook; the next run picks
it up.

## Inputs (read in this order — each must exist when relevant)

| Order | What | Where |
|---|---|---|
| 1 | **Roster** | `hr.load_roster` + `hr.load_watchlists`; `input/*.csv` holdings, `input/watchlist*.md` — `docs/TECHNICAL_ARCHITECTURE.md` Ticker lifecycle |
| 2 | **Analyst sheet** | `output/data/analyst_<date>.md` — produced today by the Analyst subagent. Do not run without it; if missing, halt. |
| 3 | **Analyst's deterministic outputs** | `output/data/facts_<date>.md`, `output/data/fundamentals_<date>.md`, `output/data/xray_<date>.md`, `output/radar/Heartbeat_Radar_<date>.md` |
| 4 | **Rulebooks (read fresh)** | `rules/01_METHOD.md`, `rules/02_SLEEVE_RULES.md`. **Stricter wins** across Method → Sleeve Rules → Watchlist; Speculative Tier is the deliberate size-limited exception. |
| 5 | **Sector map** | `input/tracking/sector_map.md` — authoritative ticker → sector + bellwether ETF table |
| 6 | **Stop-loss log** | output ledger; existing stops on held positions |
| 7 | **Methodology on exceptions** | `docs/DATA_SOURCES.md` (source contract), `output/ledger/Gate_Ledger.csv` (past gate decisions) — duplicate-detection on new positions |

**The roster is the contract for the run.** Extract it programmatically — every
symbol in `input/watchlist*.md` (or `input/watchlist.md` alone for the canonical
single-list setup) plus every holding row in the holdings CSV — and state the
total as `Coverage: N/N` in the report header. The saved report must contain
exactly one signal for every ticker on it.

> **A run that skips names is a failed run.** This rule exists because an 18-name
> gap once shipped unnoticed.

**Tracking names in `input/tracking/*.md` are not part of the daily roster.** They
are radar-screened and feed the rotation read, but the run does not allocate a
gate card to them. To evaluate a tracked name, promote it: move the row from
`tracking/universe.md` to `input/watchlist.md`, then re-run. The reverse move —
demoting a watchlist name that has never been actioned back to `universe.md` —
is a legitimate way to keep the roster honest; the name stays monitored.

> **Retire stale local caches as inputs.** Summary files generated by manual-only
> tasks drift within days and then read as current. Either check the source
> live, or don't cite it. (Full source contract: `docs/DATA_SOURCES.md`.)

The Trading Stop / Investing Stop / 150d mechanics live in `rules/02_SLEEVE_RULES.md`. The
Trader reads them fresh; do not re-state them here. **This is the boundary between
methodology (lives in rulebooks) and pipeline (lives in this file).**

## Output spec — what the report binds to

**The shape of `output/evaluation_<date>.md` is `templates/evaluation.template.md`. That
file is the only source for it, and this section deliberately does not restate it** — not
the section list, not the column sets, not the header block.

The template is the copy that is *enforced*: the Trader reads it fresh every run
(`agents/trader.md` §9) and `tools/eval_reviewer.py` check 19 diffs the report's `##`
headings against it. The description of the report shape that used to sit here was
enforced by nothing, drifted, and took the report with it — see `docs/BACKLOG.md` item 25.

What this file owns is the part that is **not** shape: the points where the report is an
interface to another tool, and the handling rules that outlive any particular layout.

1. **Headings that scripts match, rather than read.** `## Conviction-ranked action board`
   is bound by verbatim, case-sensitive regex in both `tools/eval_reviewer.py` and
   `tools/append_gate_ledger.py`; `## Held positions (summary)` is bound the same way in
   `tools/eval_reviewer.py` check 19. **Rename either and the consumers read zero rows and
   report success.** The template states the rule and the incident at the point of use
   (`docs/BACKLOG.md` item 20); what is recorded here is which files hold the regex, so a
   change to one can find the others.

2. **Gate results reach `tools/pnl.py` as a string, not as a number.** It groups blocked
   decisions by the `GATE: S 7/7` / `GATE: E fail #8` text verbatim, so the `S`/`E` card
   prefix the template mandates is a data-format contract with the ledger, not a
   presentation choice — unprefixed, two differently-numbered cards merge into one
   meaningless hit rate.

3. **Two blocks are quoted from a generated file, never recomputed.** The sector-weights
   table and the portfolio-growth chart come from `output/data/xray_<date>.md` as drawn by
   `tools/xray.py`; the radar age comes from `run_manifest.json`'s `radar.verdict`. Both
   are lookups — a report that re-derives either can disagree with its own source, which
   is the 2026-08-18 failure `tools/run_daily.py` exists to prevent.

4. **Sourcing.** Note which signals came from which source, and flag any quote or level
   that looked stale. Cite web sources as markdown links.

5. **Do not write evaluation state back into the watchlist** — it stays a stateless
   registry (invariant 1 of `docs/TECHNICAL_ARCHITECTURE.md`).

**Archive copy (optional).** If archiving to a document service, upload as a
*native document*, never a raw `.md` — most services don't render markdown and a
text upload shows literal syntax. Pass the markdown as the text content with a
markdown MIME type. **Do not backslash-escape markdown characters.** Most
connectors cannot overwrite, so each run adds a date-stamped file. **If the
archive is unreachable, note it and continue — the local save is authoritative
and is never skipped.**
